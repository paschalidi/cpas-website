Part IV — The gold standard

Achieving serializability

The strongest guarantee: the result is identical to running transactions one-at-a-time, in some order. Every anomaly above becomes impossible. Three ways databases pull it off.

Actual serial execution

VoltDB · Redis

Stop pretending. Run transactions literally one at a time on a single thread. Cheap RAM made datasets fit in memory; short OLTP transactions made it fast enough. Often shipped as stored procedures so nothing waits on the network mid-transaction.

Trade-offThroughput capped at one CPU core. Great until you outgrow a single core.

Two-phase locking

2PL · the 30-year classic

Readers and writers block each other with shared and exclusive locks, held until commit. Phantoms are caught with predicate locks (or the practical index-range lock) that lock rows matching a condition — even rows that don't exist yet.

Trade-offLots of waiting, reduced concurrency, frequent deadlocks forcing aborts and retries.

Serializable snapshot isolation

SSI · PostgreSQL · since 2008

Optimistic. Transactions run freely on a snapshot, like snapshot isolation. The database tracks read-write dependencies and, at commit, aborts any transaction whose reads were invalidated by another. Bet that conflicts are rare — usually they are.

Trade-offAborts and retries under high contention, but far less blocking than 2PL.

The throughline. Weak isolation levels are popular because they're fast — but they quietly move the burden of preventing these anomalies onto you, the developer. Getting every SELECT … FOR UPDATE and compare-and-set right by hand is exactly the subtle, hard-to-test work that breeds bugs. Serializability moves that burden back into the database. The whole chapter is an argument about where that burden should live.
